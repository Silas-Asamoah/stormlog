# Issue #118: native probe decision (protocol v2)

**Decision: defer** a direct-CUPTI collector, with measured reasons and a short list of fixes that would make it adoptable. This applies the decision rule fixed in `protocol_v2.json` before any v2 data was collected. The rule's adopt conditions were not met: p95 perturbation was +27% at the largest window (limit 5%), collector memory grew with the window, and loss visibility had gaps. The reject conditions were not met either: fidelity matched Nsight in eager and CUDA-graph execution, and perturbation was about half of Kineto's.

This replaces the 2026-10-04 interim defer, which rested on a comparison that never ran. All numbers below come from runs whose per-trial results are in `results_v2/trials.jsonl`.

## What changed from v1

v1 (`final_run_proposal.json`, now in git history at commit `dcb58a4`) could not produce a comparison:
- Direct CUPTI recorded from process start while the other profilers started after warmup.
- Memory sampling ended before the profiler stop, which is when Kineto's peak happens.
- Kineto's failure to export a 220 s window was treated as a missing denominator instead of a result.

v2 fixes each of these. Every mode starts capture when measured load starts and stops after W × 0.1 s. Sampling continues through stop and settle. Kineto's stop cost is measured rather than excluded. The pre-data amendments, and the evidence behind them, are listed in `protocol_v2.json`.

## Setup

- One JarvisLabs L4 (driver 580.126.20), vLLM 0.30.0 V1, Qwen2.5-0.5B-Instruct, eager unless noted.
- Each trial: 200 warmup and 2,200 measured streaming requests at 0.1 s offsets, fresh server per trial.
- Window scaling: 3 repetitions per mode and window, in a seeded shuffled order.
- Fidelity: Nsight Systems 2026.3.2 in separate runs.
- `cupti-min` collects runtime, driver and kernel activity; `cupti-full` adds memcpy, memset and synchronization.
- The helper links CUPTI 13.0.85, matching torch's CUDA 13 runtime.
- Exact environment: `results_v2/environment.txt`.

### Memory by domain

The owner's comment asked for each memory domain, peak and sustained. Each value is the median added over the trial's pre-capture baseline. "Sustained" is the median target-tree RSS during the window; "peak" includes stop and export.

| W | Kineto sustained / peak RSS | CUPTI-min sustained / peak RSS | CUPTI-min activity buffers (peak) | GPU memory added, Kineto / CUPTI-min |
|---|---|---|---|---|
| 50 | 121 MiB / 1.7 GiB | 8 / 16 MiB | 32 MiB | 34 / 0 MiB |
| 200 | 502 MiB / 7.3 GiB | 28 / 60 MiB | 72 MiB | 42 / 0 MiB |
| 800 | 2.0 GiB / 29.3 GiB | 116 / 234 MiB | 232 MiB | 12 / 8–12 MiB |
| 2200 | 5.4 GiB / 74.5 GiB | 366 / 726 MiB | 648 MiB | 12 / 44–52 MiB |

- Most of Kineto's peak comes from export, not capture.
- GPU memory changes were small in every mode, against a baseline of about 17.8 GiB (18,180 MiB) set by vLLM's `gpu_memory_utilization=0.8`. Values come from `nvidia-smi` sampled once per second.
- **Pinned host memory was not measured.** No v2 measurement can separate CUDA-pinned pages from other RSS, so pinned host memory is unknown for every mode.
- **No numeric memory-reduction threshold was set before data.** The comment asked for one; v2's rule only required CUPTI memory to stay bounded where Kineto's grew. Both grew, at very different rates, so the bounded-memory condition failed whatever threshold is chosen.

### Hypotheses

- **H1, cost scaling: partly supported.** Kineto's in-process memory and export time grow with the window. Its export blocks serving: about 1,400 of 2,200 requests failed or missed the 2 s SLO at W=200 and W=800, and all three W=2200 stops timed out at 600 s. CUPTI's memory also grows linearly, about 100 times more slowly. The ablation explains why: with records discarded instead of serialized, added RSS stayed at 8 MiB and stop took 0.01 s. The growth is the helper's consumer falling behind (JSON and zlib inside the CUPTI callback, about 1.1 CPU cores), not CUPTI itself.
- **H2, perturbation: relative yes, absolute no.** CUPTI-min's +25 to +27% is about half of Kineto's +51%, but far above 5%. The ablation shows the cost is in API activity tracing itself, not in the helper: discarding records still cost +26%. Kernel-only capture cost +8% but loses host-launch correlation.
- **H3, fidelity: supported, except overlap.**
  - Microbenchmarks matched Nsight with exact per-name counts: W1 3000 = 3000, W2 32000 = 32000, W3 3000 = 3000 graph-node kernels.
  - vLLM W=200 runs matched kernel name sets with 100% launch correlation in eager mode, and in CUDA-graph mode with 93.5% of kernels on graph nodes in both tools.
  - Stream overlap is untested: the W2 workload did not overlap on the L4 in either tool.
- **H4, loss visibility: not met.**
  - Output-limit drops were reported.
  - A slow consumer grew the backlog (72 MiB, 224 s flush) instead of dropping visibly.
  - With Nsight attached, the helper captured 0–1 records yet reported a clean finalize.
  - CUPTI 12.6 under the CUDA 13 runtime silently lost about 39% of kernel timestamps while reporting 0 drops. The helper now counts timestamp-less kernels.

### Post-hoc: CUDA-graph perturbation (not part of the decision rule)

Added after the eager results, so it does not change the decision above. vLLM ran with CUDA graphs (its default serving mode) at W=200, 3 repetitions per mode, against graph-mode `off` (`results_v2/graph_perturbation.md`):

| mode | window p95 Δ | added RSS | stop | records |
|---|---|---|---|---|
| cupti-min | +0.8% [−0.0%, +1.2%] | 62 MiB | 0.46 s | 3.8M |
| cupti-kernel | +1.1% [+1.0%, +1.2%] | 62 MiB | 0.29 s | 1.4M |
| off | 0.0% [−0.1%, +0.8%] | 0 | – | – |

Graph replay replaces most per-kernel API calls, so there are about 2.6 times fewer records than in eager mode at the same window. Perturbation falls inside the range of `off`-to-`off` variation. This suggests the eager +25% is mostly an eager-mode cost, but it was observed at one window and decided after the fact. A pre-declared run at larger windows is needed before it can support adoption. Both CUPTI modes added about 62 MiB in graph mode, compared with 2 to 60 MiB in eager. The source of the extra memory, beyond the 24 MiB of activity buffers, was not measured.

## Field accounting for direct CUPTI

The owner's comment asked which of the 24 matrix fields were validated, accepted as limitations, or left unqualified. Each field's role is the disposition in `protocol_v2.json`, carried over unchanged from v1 and set before any v2 data; statuses are in `matrices/stormlog_validated.json`, and each validated cell links its evidence files by checksum.

- **Validated (10):**
  - decision-critical: `signal`, `linux`, `nvidia` (L4 only), `host_api_timing`, `device_execution_timing`, `cpu_gpu_correlation`, `kernel_identity`, `graph_replay`, `engine_coupling`
  - accepted limitation: `startup_injection`
- **Measured, not met (2):** `buffer_loss_visibility`, `profiler_coexistence`. Both are decision-critical.
- **Measured, version-dependent (1):** `runtime_coupling` (decision-critical). CUPTI must match the target's CUDA runtime.
- **Unqualified, decision-critical (5):**
  - `streams`: overlap not exercised
  - `containers`, `privileges`, `packaging_complexity`: one root container only
  - `support_burden`: not measured
- **Unqualified, accepted limitations (6):** `amd`, `macos`, `windows`, `late_attach`, `semantic_inference_phases`, `instruction_level_detail`.

For Kineto, v2 validated `linux`, `nvidia` and `late_attach`; its cost results are in the table above. The other six candidates were not run in v2; their cells are unchanged.

## What would make direct CUPTI adoptable

1. **Bound the consumer.** Cap outstanding activity buffers so CUPTI drops and reports records instead of growing memory. Move encoding off the callback thread and use a binary record format. Target: the flat 8 MiB and sub-second stop the discard ablation showed.
2. **Ship the CUPTI that matches the target's CUDA runtime.** For example, load it from the target environment's `nvidia-cuda-cupti`, and fail closed when the major versions differ.
3. **Detect lost subscriptions.** When another CUPTI client (Nsight, Kineto) takes the process, report it instead of finalizing an empty capture.
4. **Re-measure perturbation on the deployment configuration** with a pre-declared CUDA-graph window-scaling run. The post-hoc W=200 result was +0.8%. Also qualify stream overlap with a workload that actually overlaps on the target GPU.

## Implications now, independent of native probes

- vLLM's torch profiler is only safe for short windows. On this L4 workload, a 5 s window cost 1.7 GiB and a 33 s serving stall, and a 20 s window cost 7.3 GiB and a 138 s stall. Stormlog's existing PyTorch profiler integration should document a short bounded window as the supported use.
- Any CUPTI-based capture must match the target's CUDA runtime, or kernel timing can disappear without a reported drop.

## Unchanged scope limits

- One GPU model, one engine version and one model, run as root in one container image.
- AMD (#235), macOS and Windows remain unqualified.
- No request or phase attribution was tested; CUPTI records have no inference semantics by themselves.
- Three repetitions per cell, reported as ranges, not confidence intervals.
